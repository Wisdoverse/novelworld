# ADR 0002: L0-L4 minimal bootstrap and deferred runtime configuration

- Status: Accepted
- Date: 2026-08-25
- Owners: deployment, user-service, agent-service, gateway, and frontend owners
- Related: [`../../DEPLOY.md`](../../DEPLOY.md); [`../PRODUCT_CONTRACT.md`](../PRODUCT_CONTRACT.md)

## Context

The server launcher currently generates credentials for PostgreSQL, Redis, JWT
signing, runtime-configuration encryption, and service-to-service calls without
an explicit first-install commit boundary. The
base Compose topology also waits for Redis before Agent Service can become
ready. At the product boundary, the first-run page couples the single-winner
administrator bootstrap to a live model-provider connection test. These
requirements make reconstructable infrastructure and mutable product settings
look like process bootstrap roots.

PostgreSQL is authoritative for application state. Agent Service already has a
safe `memory://` adapter that skips the Redis projection, and the shared LLM
client already resolves an encrypted User Service-owned configuration through
authenticated internal HTTP on each provider-backed operation. The smallest
coherent change is to expose those existing paths in the default deployment and
first-run journey.

This decision does not add a configuration service, move deployment secrets
into the application database, dynamically switch cache adapters in a running
process, make S3 non-authoritative after retained objects exist, or claim
multi-region/public-hosted availability.

## Decision

Configuration is classified by ownership and failure semantics:

| Level | Meaning | Examples | Missing or unreachable behavior |
|---|---|---|---|
| L0 | Installation bootstrap required before any runtime starts | Bundled PostgreSQL user, database name, generated database password, and the local completion marker | An interactive first launch guides the operator, persists validated values with the marker written last, and restarts the launcher before Docker or any business service starts. A valid preseed or existing installation migrates without a prompt; an unconfigured non-interactive launch fails closed. |
| L1 | Immutable runtime roots of trust | JWT signing secret, runtime-configuration encryption key, internal service identity, and the database connection derived from L0 | Fail before serving traffic. Secret values are generated by the launcher or supplied by the orchestrator/secret manager and never loaded from the application database. |
| L2 | Deployment topology and security posture | bind address, service URLs, CORS origins, token lifetime, rate limit, enabled storage/cache mode | Safe defaults may be supplied by the deployment profile. Mode selectors introduced or changed by this decision fail closed when malformed or half-selected; other existing fields retain their current parsing contracts. These values are not a cross-service database concern. |
| L3 | Owner-managed mutable product configuration | model provider, model, API key, thinking mode | Services become ready without it. User Service owns and encrypts it in PostgreSQL; consumers load it only through the authenticated internal API. Missing configuration gives the provider-backed operation a bounded typed failure. |
| L4 | Optional or reconstructable capability | Redis projection when disabled, monitoring, embeddings, image generation | Absence does not block the base profile. Explicitly enabled capabilities retain their own validation and failure contract. |

L0 is deliberately a launcher concern, not an unauthenticated browser endpoint.
The bundled Compose host and port remain fixed; the guide asks only for a
lowercase PostgreSQL role and database name and generates a non-placeholder
URL-safe password. `BOOTSTRAP_L0_COMPLETE=true` is the commit point and is
accepted only while all three database values still validate. The launcher
then re-executes once, generates L1 roots, starts the selected profile, and
waits for readiness. It never exposes Docker control or stores a database
credential inside the database it is needed to open.

`CACHE_MODE` is the single deployment-owned cache selection surface. Its only
supported values are `postgres` and `redis`. The base profile persists
`CACHE_MODE=postgres`, selects Agent Service's existing `memory://` adapter, and
does not start, address, or wait for Redis. `CACHE_MODE=redis` atomically selects
the Redis Compose profile, requires a non-placeholder Redis credential, injects
the Redis URL, and includes Redis in Agent and Gateway readiness. A half-selected
mode fails launcher validation instead of silently degrading. Installations
created before this decision that have a Redis credential but no `CACHE_MODE`
are migrated once to `redis`; new installations default to `postgres`.

Selection happens only at process start and is persisted in the deployment
environment so a restart cannot silently change adapters. A configured Redis
outage continues to fail Agent readiness. There is no automatic runtime fallback
because Redis tombstones and projection state need a separately designed
transition protocol. Release deployment, rollback, health checks, and capacity
qualification all read the same mode. Capacity qualification explicitly selects
`redis`; it is not evidence for the minimum profile.

S3 remains disabled by default. Once retained source objects or pending source
deletions exist, S3 is a conditional hard dependency and Novel Service keeps its
existing fail-closed startup/readiness behavior. Object-store credentials,
Redis credentials, database credentials, signing keys, encryption keys, and
workload identity secrets are deployment secrets, not L3 database settings.

Initial setup commits only the unique administrator and its refresh token. It
does not require an LLM setting or provider call. `GET /setup/status` treats the
administrator as completion of bootstrap and reports LLM configuration
separately under a bumped response contract. The administrator may later create
or update LLM settings through the existing protected settings endpoint; the
API key is validated, connection-tested, encrypted, and saved by User Service.
The next provider-backed operation observes the database value without a
service restart. Environment-managed LLM configuration remains a supported,
read-only deployment override.

A synchronous Agent or Narrative generated-turn endpoint with no effective LLM
configuration returns HTTP `503` with code `llm_not_configured`. This is
distinct from a configured provider outage, which retains its existing `502
llm_error` contract. Agent and Narrative services may retain failed
idempotency/audit claims, but must not mark
a turn completed or commit generated messages, choices, consequences, or world
state. Novel import is asynchronous: it may durably retain the submitted source,
deterministically split chapters, and a failed import job for retry, but must not
mark the novel ready or commit provider-generated characters, relationships, or
other derived success state. The failure reason identifies missing configuration
separately from provider unavailability.

Frontend changes remain in the existing FSD layers: application bootstrap
gating stays in `app`, the first-run screen stays in `pages/setup`, mutable model
configuration stays in `pages/settings`, authentication remains a `features`
slice, and transport remains in `shared/api`. Setup status and settings are
server state and therefore use TanStack Query queries/mutations with explicit
invalidation; component-local state is limited to form drafts. No layer imports
upward.

## Alternatives considered

- Retaining Redis and LLM setup as default hard dependencies was rejected
  because both already have explicit non-authoritative/deferred paths and do
  not own committed application state.
- A generic configuration table or new configuration microservice was rejected
  because User Service already owns the only requested cross-service runtime
  setting. It would add a service boundary without a second demonstrated use.
- Letting every service read a shared configuration table was rejected because
  a shared PostgreSQL deployment does not waive bounded-context ownership;
  cross-service reads use HTTP adapters.
- Automatically falling back from a configured Redis instance at runtime was
  rejected because silent adapter transitions can violate deletion-tombstone
  and projection semantics.
- Treating S3 as always optional was rejected because retained source replay and
  deletion become durable obligations once database rows reference the bucket.
- Storing L1/L2 secrets in PostgreSQL was rejected because database credentials
  cannot bootstrap from that database and co-locating ciphertext with its root
  key removes the intended security boundary.

## Consequences

A clean interactive installation guides the operator through L0 PostgreSQL
identity, automatically generates the database credential and L1 roots, then
brings the base stack to ready after one launcher restart. The initial administrator can enter the
application before purchasing or configuring a model provider. AI-backed
operations remain unavailable until L3 configuration exists; they must not
report success or create partial authoritative state.

The default server profile no longer provides Redis short-term projection.
Recent committed chat still comes from PostgreSQL, matching the existing
portable-desktop contract. Operators who explicitly enable Redis retain the
current cache behavior and readiness signal. Redis remains part of release
artifacts and integration coverage even though it is not part of the minimum
base profile.

The public setup-status contract changes and old/new frontend-backend pairs
fail closed on the contract number. The protected model-settings update becomes
an upsert: its first write requires a non-empty API key; later writes may retain
the encrypted key. An environment-managed setting is displayed read-only. No
database migration is required because the existing singleton
runtime-configuration row is already optional.

## Rollout and rollback

Ship the setup-status contract bump, one-step frontend bootstrap, settings
upsert, base `memory://` selection, optional Redis profile, launcher readiness
wait, documentation, and tests in one release. Mixed frontend/backend versions
show the existing configuration-service error instead of guessing setup state.

Success signals are: the minimum-profile Compose smoke reaches Gateway
readiness without Redis or an LLM key; first-admin creation performs no provider
call; an administrator can save the first LLM configuration and the next LLM
operation observes it; the explicit Redis profile and S3 recovery drills retain
their prior semantics.

Abort on a setup takeover regression, a provider call during minimum bootstrap,
an authoritative chat/import/world commit that depends on the disabled Redis
projection, a retained-source deployment that becomes ready without its bucket,
or a launcher that reports success before Gateway readiness.

Administrators and encrypted runtime settings created by the new release remain
schema-compatible. Rollback to a release that predates this decision is guarded
before any service replacement because its setup and Redis assumptions are not
compatible with every new installation. The release script refuses that rollback
unless both conditions are true:

1. an effective LLM configuration exists, either as a validated
   operator-managed environment override or as a User Service-owned value that
   the still-running current User Service proves it can decrypt: the rollback
   guard first proves that process has no environment override, then calls the
   existing authenticated runtime LLM endpoint and accepts only HTTP `200`
   while discarding its response body; and
2. `CACHE_MODE=redis`, a non-placeholder Redis credential is persisted and can
   authenticate the healthy Redis container before the old Agent Service is
   started.

The guard consumes only the endpoint status and never reads or prints its body,
encrypted key, or ciphertext. If the current User Service is
unavailable and there is no valid environment override, rollback refuses and
requires repair of the L1 root or forward recovery. An operator may satisfy the
guard while the current release is still running, then retry rollback. The
script does not invent a Redis password or guess an LLM setting during rollback.
Rollback to a release containing this decision preserves the persisted cache
mode and uses the normal mode-aware health checks.

## Evidence

- Launcher self-checks pin fail-closed non-interactive L0, validated preseed
  migration, marker-last commit, automatic restart, generated L1 secrets,
  blank deferred-provider keys, atomic and restart-stable cache selection,
  migration ordering, and success
  only after Compose readiness. Negative startup tests reject blank, weak, and
  documented-placeholder JWT/internal-service roots. User Service also
  decrypts any existing runtime configuration before binding, so a wrong but
  syntactically valid 64-hex encryption key fails startup.
- The production Compose smoke boots with no Redis profile and no LLM, S3, or
  monitoring configuration; an explicit `CACHE_MODE=redis` path retains cache,
  restart, and outage coverage. The minimum path asserts the absence of a Redis
  container.
- User Service tests pin administrator-only setup completion, first protected
  settings upsert, no overwrite after a rejected provider test, and startup
  failure when an existing encrypted setting cannot be decrypted.
- Frontend unit and browser accessibility tests pin the one-step bootstrap,
  missing-model settings state, environment-managed read-only state, TanStack
  Query ownership, FSD imports, and keyboard completion.
- Agent and Narrative tests pin the missing-configuration status/code separately
  from provider outages; Novel import tests pin its allowed durable-failure
  boundary.
- Release tests pin the pre-decision rollback refusal and the successful guarded
  rollback path without exposing encrypted configuration.
- Provider-outage, S3 recovery, secret-rotation, PostgreSQL/Redis integration,
  and required CI remain authoritative for their existing boundaries.
